**Steve, 2026-07-27 (launch morning), replacing the old APPROVAL-REQUIRED rule that
lived in this file:** *"Remove my standing approval required for posts... That is a
nonsensical rule that undercuts me trusting you. Publishing is now preapproved WITH
a small OPTIONAL request to review the posts before they go live. The process for
content creation is a step-by-step methodical co-creation — I'm involved the whole
time — it's always got my eyes on it — I don't have to gate the final product. This
is an example of a bad rule."*

**Why:** the per-post gate double-charged Steve for oversight he already exercises
during co-creation. A rule that only adds friction with no failure it prevents is
clutter (his own Constitution R4), and this one actively signaled distrust. (The
2026-04 incident that birthed the old rule — an unreadable dark-on-dark carousel —
is better prevented by the co-creation process itself than by a final gate.)

**How to apply:**
- Content co-created in session → **post / publish / schedule directly.** Offering a
  pre-flight look ("want eyes on it before it goes live?") is an OPTIONAL courtesy,
  never a blocking gate. Don't ask-and-wait; post, or offer-and-proceed.
- **Channel scoping still applies** (this is scope, not a gate): publish only to
  channels Steve has authorized — X @HiSteveKaplan, LinkedIn personal
  (stevekaplanai), and any channel he names per-project. A never-authorized surface
  (GTMVP page, client accounts, new platforms) is out of scope until he adds it.
- Content Steve has NOT seen at all (fully autonomous generation) → lean toward the
  optional review offer, still not a hard gate.
- **Applies to every AI Steve works with:** desktop Claude (Postiz/Blotato/Slack
  MCP posting), the box agents (the charter's social exception already auto-runs
  posting tasks — aligned), Hermes, and launch-thread replies (the launch-day
  briefing's "Steve approves every reply" step is superseded — see the edited vault
  note).
