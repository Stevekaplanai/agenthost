**Steve's insight (2026-06-03):** third-party measurement / server-side tracking tools like **Elevar** (also Stape, server-side GTM, etc.) are **complementary integration points**, not competitors — they solve the **tracking problem AttriByte will face often** (cookie loss, iOS/ITP, ad-blockers, weak client-side pixels). This directly answers AttriByte's own "no-pixel / cookie-death / how do you measure CPA" gotcha.

**Why it fits (the strategic logic):** AttriByte is the cross-channel **attribution + measurement** layer; it needs clean conversion/identity/touchpoint data to attribute. Elevar already produces exactly that — **server-side, high-match-rate conversion events + identity stitching** (Shopify-centric: it server-side-forwards purchases to GA4/Meta/etc. with strong identity). So Elevar = a high-quality **SOURCE of conversion touchpoints/events** feeding AttriByte's attribution, instead of AttriByte trying to solve first-party tracking itself. It plugs the exact gap flagged in the proxy build: **AttriByte has no first-party touchpoint/events ingestion sink yet** (`runSyncType` only sinks accounts/contacts/opportunities/campaigns/ad_spend). Elevar-class data would feed a NEW touchpoint/events sink → enables true multi-touch DDA (Markov/Shapley) instead of platform-reported-only CPA.

**Integration-path caveat (different from the 15 catalog adapters):** Elevar is almost certainly **NOT in Pipedream's Connect catalog**, so it does **not** fit the proxy-adapter pattern. It needs either (a) a **direct API integration** (Elevar has APIs / data exports) or (b) **webhook/event ingestion** (Elevar pushes events to a destination → AttriByte as a server-side destination). Either way it pairs with building the **events/touchpoint ingestion sink** (the deferred work). So this is its own workstream: "server-side conversion-data sources," distinct from the Pipedream-proxy CRM/ad adapters.

**Status (updated 2026-06-03): SCOPED — build-ready design doc shipped (PR #183).** Steve approved scoping BOTH Elevar + Stape. Doc: `Projects\attribyte\docs\server-side-tracking-integrations-plan.md` (on main). **Key findings that change the earlier plan:**
- **Both integrate as a server-side DESTINATION** (the customer FORWARDS events to AttriByte). Neither has a usable PULL/read API — pull is a dead end for both. Elevar forwards via **Google Cloud Pub/Sub** (no generic webhook destination exists; AttriByte attaches a push subscription). Stape forwards via a **GTM-SS HTTP Request tag** the customer adds in their sGTM (arbitrary URL + auth header; host-agnostic, no Stape API/partnership needed).
- **NO new sink needed (corrects my earlier assumption).** The EXISTING live path `POST /api/v1/events/batch` (the SDK path, `apps/api/src/routes/events.ts`) already runs event→touchpoint→DDA synchronously. Server-side events POST there with zero schema change. **Do NOT use the Go collector** (`apps/collector`) — its Event struct has no eventId/clickIds, Kafka isn't consumed, worker writes phantom columns.
- **The real gap = IDENTITY.** A touchpoint is created only when `contact_id` resolves (`touchpoint-creator.ts`); a server-side event with no userId/email is stored but never enters DDA. Forwarded events MUST carry identity.
- **Workspace routing:** Stape = per-workspace `X-API-Key` header the customer pastes into the tag; Elevar = which Pub/Sub subscription the message arrives on.
- 4-phase plan in the doc: P1 ingest edge + workspace key, P2 Elevar Pub/Sub adapter (gated on capturing one live message — Elevar's docs render cookies{}/landingSite{}/consent/email empty, so click-ID/UTM/consent key names are UNCONFIRMED), P3 Stape GTM tag template + mapping guide, P4 touchpoint→DDA validation.
- **PHASE 1 BUILT (PR #184 merged 2026-06-03, 8eb0597).** Shipped: shared ingest primitive `apps/api/src/lib/event-ingest.ts` (extracted from events.ts — SDK routes UNCHANGED, only applyPrivacy lifted out); `apps/api/src/routes/ingest.ts` with **`POST /api/v1/ingest/stape`** (X-API-Key auth) + **`POST /api/v1/ingest/elevar/:writeKey`** (write key in path; GCP Pub/Sub push can't set headers; validated via the same hashed-key lookup; 200-fast on undecodable msg, 5xx→Pub/Sub retries real failures); pure normalizers `lib/vendor-ingest/{stape,elevar}-normalizer.ts` (18 unit tests). **workspace_id always from the authenticated key, never the payload.** Reuses the existing event→touchpoint→DDA chain (no forked attribution). Reviewed clean (the flagged HIGH — event-ingest 500 vs SDK 400 — was VERIFIED a non-issue: SDK keeps its own BadRequestError path; the ingest edge's 500-on-DB-failure is correct for Pub/Sub retry).
- **ALSO shipped in #184: the pull-activities→touchpoint sink** — `runSyncType` now handles `'activities'`/`'events'` via reused historical-reconstruction Rule-3; added to SYNC_TYPES_BY_PROVIDER for salesforce/hubspot/bitrix24 ('activities') + posthog ('events').
